# ITSI Bidirectional Ticketing Integration API Guide

This guide documents the exact REST API paths, payload formats, and schemas required to implement bidirectional ticket synchronization between Splunk ITSI Episodes and an external ticketing gateway (e.g. a custom in-house ITSM, Jira, ServiceNow, etc.) without relying on the official out-of-the-box add-ons.

---

**Validated on:** ITSI 4.21.x. Not re-verified on ITSI 5.0.

## Architecture Overview

ITSI Episode Review acts as a state manager and frontend aggregator. Its data is stored across two layers:
1. **The KV Store (Episode Metadata & Relationships):** High-level properties (status, owner, severity) and associations (external ticket links, comments) reside in the KV store collections.
2. **The Indexers (Notable Events):** The raw events and custom fields generated by Correlation Searches reside in the `itsi_tracked_alerts` index.

To synchronize an external ticket queue with ITSI, the ticketing system must query the indexers to extract incident metadata, and write updates back to specific KV store collections.

## API Operations

### 1. GET Episode notable event custom fields
Because the episode KV store does not contain the notable event details (like `src`, `hostAlias`, or custom fields from Zabbix/Checkmk), the integration must run a search against the indexer.

* **Endpoint:** `/services/search/jobs/oneshot?output_mode=json`
* **Method:** `POST` (Form-encoded body)
* **Payload:**
```bash
curl --location -X POST 'https://<itsi-sh-host>:8089/services/search/jobs/oneshot?output_mode=json' \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'search=search index=itsi_tracked_alerts itsi_group_id="<itsi_group_id>"'
```
* **Output:** Returns a list of notable events in the episode, where `_raw` contains the JSON representation of all custom fields.

---

### 2. POST to update Assignee (Owner) or State (Status)
To change status/assignee, perform a partial update on the specific episode.

* **Endpoint:** `/servicesNS/nobody/SA-ITOA/event_management_interface/notable_event_group/<itsi_group_id>?is_partial_data=1&output_mode=json`
* **Method:** `POST` (JSON body)
* **Status mapping:** `1` = New, `2` = In Progress, `3` = Pending, `4` = Resolved, `5` = Closed.
* **Assignee gotcha:** The `owner` must match a **valid registered Splunk username** (often an email address like `user@domain.com` or `unassigned`), or the update is silently rejected.
* **Payload:**
```bash
curl --location -X POST 'https://<itsi-sh-host>:8089/servicesNS/nobody/SA-ITOA/event_management_interface/notable_event_group/<itsi_group_id>?is_partial_data=1&output_mode=json' \
  --header 'Content-Type: application/json' \
  --header 'Authorization: Bearer <token>' \
  --data '{
    "status": "4",
    "owner": "first.last@example.com"
  }'
```

---

### 3. POST External Ticket Number & Link (All Tickets Section)
ITSI renders linked tickets in the "All Tickets" panel of Episode Review by reading from the `itsi_notable_event_ticketing` KV store collection.

* **Endpoint:** `/servicesNS/nobody/SA-ITOA/storage/collections/data/itsi_notable_event_ticketing/<itsi_group_id>`
* **Method:** `POST` (JSON body)
* **Nested Array Schema Gotcha:** While lookup transforms reference dot-notated fields (like `tickets.ticket_id`), the actual document must store them as a **nested JSON array of objects** under the `tickets` key to satisfy the JavaScript UI parser:
```bash
curl --location -X POST 'https://<itsi-sh-host>:8089/servicesNS/nobody/SA-ITOA/storage/collections/data/itsi_notable_event_ticketing/<itsi_group_id>' \
  --header 'Content-Type: application/json' \
  --header 'Authorization: Bearer <token>' \
  --data '{
    "_key": "<itsi_group_id>",
    "event_id": "<itsi_group_id>",
    "ticket_system": "AcmeITSM",
    "tickets": [
      {
        "ticket_id": "ITSM-INC-12345",
        "ticket_url": "http://203.0.113.10:8089/itsm/tickets/12345",
        "ticket_system": "AcmeITSM"
      }
    ],
    "object_type": "notable_event_ticketing"
  }'
```

---

### 4. POST to add comments (Activity log)
Episode comments are written directly to the `itsi_notable_event_comment` collection.

* **Endpoint:** `/servicesNS/nobody/SA-ITOA/storage/collections/data/itsi_notable_event_comment`
* **Method:** `POST` (JSON body)
* **Payload:**
```bash
curl --location -X POST 'https://<itsi-sh-host>:8089/servicesNS/nobody/SA-ITOA/storage/collections/data/itsi_notable_event_comment' \
  --header 'Content-Type: application/json' \
  --header 'Authorization: Bearer <token>' \
  --data '{
    "itsi_group_id": "<itsi_group_id>",
    "comment": "Ticket created in the ITSM with ID ITSM-INC-12345.",
    "time": "1782833787",
    "user": "itsm_system"
  }'
```
*(Note: `time` must be an epoch timestamp as a string).*

## Agent Workflow Checklist

When assisting a user setting up bidirectional ticketing:
- [ ] Verify that they target `itsi_tracked_alerts` index for GET operations (not `notable`).
- [ ] Guide them to use `/services/search/jobs/oneshot` instead of GET on `/services/search/jobs`.
- [ ] Confirm the target user account email exists in Splunk authentication when updating the assignee.
- [ ] Ensure they POST the ticketing link using the nested array structure under the `tickets` key.
- [ ] Advise that browser cache page reloads are required to see the updates reflect in Episode Review.
